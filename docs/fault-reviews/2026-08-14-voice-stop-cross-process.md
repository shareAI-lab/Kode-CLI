## 1. 问题描述

### 1.1 问题场景

一个 TUI 进程正在播放语音时，用户在另一个终端执行 `kode voice stop`。

### 1.2 具体表现

新进程拥有自己的模块变量，始终显示 `No active voice playback.`，不会停止原 TUI 的播放。

### 1.3 错误信息

无进程间通信错误；错误是命令声明的停止能力不可达。

## 2. 临时解决方案

未引入不完整的 PID 或控制文件方案；继续使用同一 TUI 内的 `/voice stop`。

## 3. 根本原因分析

### 3.1 问题分析过程

1. CLI `stop` action 调用了 `interruptVoicePlayback()`。
2. 该函数仅检查当前 Node/Bun 进程的模块级播放句柄。
3. 外部 `kode` 调用启动的是新进程，无法共享该句柄。
4. 所以命令成功退出但没有控制播放进程。

### 3.2 直接原因

`kode voice stop` 把进程内 API 当作了跨进程控制接口。

**相关代码位置**：`apps/cli/src/entrypoints/cli/cliParser/commands/voice.ts:38-49`；可工作的 TUI 内停止路径为 `apps/cli/src/commands/builtin/voice.tsx:344-356`。

### 3.3 根本原因

- **设计层面**：CLI 控制面没有 daemon、socket、PID 信号或控制文件协议。
- **开发层面**：命令实现没有确认调用者与播放器是否同一进程。
- **流程层面**：缺少双进程真实命令验收。

### 3.4 为什么没有提前发现

- 单进程函数调用能返回正确布尔值，掩盖了进程边界。
- 没有把“命令注册存在”与“能控制目标 TUI”分开验收。

## 4. 解决方案

### 4.1 根本解决方案

删除不可兑现的 `kode voice stop` 子命令及其进程内导入，只保留 `kode voice status`；TUI `/voice stop` 继续直接操作所属进程的播放句柄。

**修改文件**：`apps/cli/src/entrypoints/cli/cliParser/commands/voice.ts`、`apps/cli/src/entrypoints/cli/cliParser/commands/voice.test.ts:6-13`

### 4.2 影响范围评估

移除了一个始终误导用户的外部命令。未来若需外部停止，必须先设计并验证显式 IPC 协议。

## 5. 预防措施

### 5.1 代码层面

- [x] 不再把模块级状态导出为跨进程 CLI 控制能力。
- [ ] 新增外部控制前必须定义鉴权、目标选择和失效清理的 IPC 协议。

### 5.2 测试层面

- [x] 增加命令注册测试，确保不会重新暴露 `stop`。
- [ ] 若未来实现 IPC，增加两个独立进程的集成测试。

### 5.3 监控层面

- [ ] IPC 实现后记录控制请求的目标进程和实际执行结果。

### 5.4 流程/规范层面

- [ ] CLI 评审需明确每个控制命令的状态归属与进程边界。

## 6. 经验总结（一句话）

进程内取消句柄不能承诺为跨进程控制命令，未设计 IPC 时应只暴露本进程可验证的能力。
