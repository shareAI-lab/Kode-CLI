## 1. 问题描述

### 1.1 问题场景

自动化脚本查询一个不存在的目标。

### 1.2 具体表现

命令输出 `No goal found`，但最终以 0 退出，导致脚本把失败误判为成功。

### 1.3 错误信息

```
No goal found: <goalId>
exit code: 0（修复前）
```

## 2. 临时解决方案

未采用临时绕过。

## 3. 根本原因分析

### 3.1 问题分析过程

1. 缺失记录分支正确设置了 `process.exitCode = 1`。
2. 分支结束后仍无条件执行 `process.exit(0)`。
3. 显式退出码 0 覆盖前一行的失败状态。
4. 成功输出与失败输出使用了同一个收尾路径。

### 3.2 直接原因

失败分支没有提前返回。

**相关代码位置**：`apps/cli/src/entrypoints/cli/cliParser/commands/goal.ts:61-87`

### 3.3 根本原因

- **设计层面**：命令的输出和退出语义未封装为同一结果。
- **开发层面**：在设置 `exitCode` 后遗漏了控制流终止。
- **流程层面**：没有断言缺失资源的实际进程退出码。

### 3.4 为什么没有提前发现

- 人工检查只看到错误文本。
- CI 场景未覆盖命令状态码。

## 4. 解决方案

### 4.1 根本解决方案

缺失目标分支设置失败码后立即返回；只有成功读取并打印目标时才调用 `process.exit(0)`。

**修改文件**：`apps/cli/src/entrypoints/cli/cliParser/commands/goal.ts`、`apps/cli/src/entrypoints/cli/cliParser/commands/goal.test.ts:6-42`

### 4.2 影响范围评估

缺失目标现在正确向 shell、脚本和 CI 传递失败；成功查询行为不变。

## 5. 预防措施

### 5.1 代码层面

- [x] 失败分支在设置退出码后直接返回。
- [ ] 新命令优先返回结构化结果，由统一入口决定退出码。

### 5.2 测试层面

- [x] 增加断言退出码为 1 且没有调用成功退出的命令测试。

### 5.3 监控层面

- [ ] 发布脚本继续记录子命令退出码。

### 5.4 流程/规范层面

- [ ] CLI 审查清单增加失败输出与非零退出码的一致性检查。

## 6. 经验总结（一句话）

CLI 的错误文本不是失败语义，所有失败路径都必须保留非零退出码直到进程结束。
