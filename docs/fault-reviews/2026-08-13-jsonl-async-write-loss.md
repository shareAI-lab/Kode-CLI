## 1. 问题描述

### 1.1 问题场景

调用 `appendJsonlAsync()` 后，目标路径在异步追加阶段不可写（例如目标实际是目录、权限变化或存储故障）。调用方继续运行，随后通过 `flushJsonlWrites()` 进行受控收尾。

### 1.2 具体表现

原实现会清空待写队列，并在 Promise 链末端捕获后忽略错误。因此 `flushJsonlWrites()` 会成功返回，调用方误以为数据已落盘；已出队的条目既不在待写集合中，也不会由退出钩子补写。

可复现命令：

```sh
bun -e "const { appendJsonlAsync, flushJsonlWrites } = await import('./packages/core/src/utils/jsonlWriter.ts'); appendJsonlAsync({ filePath: '/tmp', entry: '{\\\"probe\\\":true}\\n' }); await flushJsonlWrites('/tmp')"
```

修复前该命令会成功完成；修复后会明确返回 `EISDIR`。

## 2. 根本原因分析

### 2.1 问题分析过程

1. 审计发现异步写入链在清空 `pending` 后吞掉 `appendFile()` 的异常。
2. 使用目录 `/tmp` 作为追加目标，稳定触发 `EISDIR`，验证 flush 未暴露失败。
3. 检查退出逻辑，确认它只处理仍在 `pending` 的数据，不能恢复已经交给 Promise 链的批次。
4. 同时检查后续写入顺序，确认失败批次必须先于新批次重试，不能因恢复而重排 JSONL 事件。

### 2.2 直接原因

`packages/core/src/utils/jsonlWriter.ts:124-165` 现在保留每个已调度批次；修复前该位置的异常处理只让 Promise 链恢复，没有保留失败数据或让 flush 失败。

### 2.3 根本原因

- 设计层面：把“调用非阻塞”和“失败可丢弃”混为一谈，缺少一个由 flush/退出路径读取的未确认写入账本。
- 开发层面：只验证了正常写入、同文件合并和目录创建，没有注入可重复的 I/O 失败。
- 流程层面：持久化辅助函数没有把“受控收尾必须失败可见”列为验收条件。

### 2.4 为什么没有提前发现

原测试仅覆盖成功路径；没有验证 `EISDIR`、恢复后顺序重放，或同步读取路径失败后的补偿。

## 3. 解决方案

### 3.1 根本解决方案

- 使用 `scheduled` 保存从 `pending` 移交给异步链、但尚未确认落盘的所有批次。
- 使用 `failed` 保留最近失败批次；后续写入或显式 flush 必须先重试它，保证文件内顺序。
- `flushJsonlWrites()` 不再吞掉拒绝；失败会传回调用方。
- 退出钩子重放 `pending` 和 `scheduled`，避免等待队列中的批次遗漏。
- 同步读取路径失败时也将该批次登记为已调度，允许稍后的异步 flush 恢复。

相关代码：

- `packages/core/src/utils/jsonlWriter.ts:12-20`
- `packages/core/src/utils/jsonlWriter.ts:124-229`
- `packages/core/src/utils/jsonlWriter.ts:236-276`
- `packages/core/src/utils/jsonlWriter.test.ts:76-111`

### 3.2 影响范围评估

成功路径仍保持按文件串行、每 tick 合并和非阻塞调用。受控 flush 现在会拒绝 I/O 错误；这是刻意的兼容性收紧，调用方可据此报告或重试，而不再获得错误的“已持久化”信号。

## 4. 预防措施

### 4.1 代码层面

- [x] 将未确认异步写入与失败状态显式建模。
- [x] 保证恢复批次先于后续批次落盘。
- [ ] 为关键持久化调用点逐步接入可观测的受控 flush。

### 4.2 测试层面

- [x] 覆盖异步 `EISDIR` 失败、失败后恢复及顺序。
- [x] 覆盖同步读取路径失败后的恢复。
- [ ] 为进程显式退出期间的排队批次增加子进程回归测试。

### 4.3 监控层面

- [ ] 在应用层记录受控 flush 的失败计数与目标类别，避免记录敏感文件路径或内容。

## 5. 经验总结

异步持久化可以不阻塞调用者，但不能把“尚未确认写入”从失败处理和退出补偿中移除。
